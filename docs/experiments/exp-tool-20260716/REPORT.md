## 3. 关键发现

### 3.1 假设验证：工具差异是否导致显著质量差异？

**结论（中低置信度）：未观察到工具间存在统计显著的森林质量差异。**

- 两工具综合分接近：
  - 按"全维度均值"口径：opencode 6.6 vs CodeBuddy（含 Hy3）6.5，**差 0.1**（更小）。
  - 按"综合分均值"口径：opencode 6.6 vs CodeBuddy 主评 6.2，差 0.4（Hy3 草稿口径）。
- 0.1–0.4 分的差距均落在**评审者间自然方差**（±1）范围内，不足以断言工具造成质量差异。
- 差异主要体现在**组织策略**与**规模**上（统一森林 + 22 叶 vs 按源分森林 + 64 叶），而非内容质量维度。

> **【MiniMax-M3 复核观察：差值口径选择】** Hy3 草稿写"差 0.4"是按"综合分均值"对比（6.6 vs 6.2），这隐含了"只看主交叉评审、不含 Hy3"的选择性。若按更稳健的"全维度均值"对比（6.6 vs 6.5），差值仅 0.1。两种口径方向一致（opencode 略高），但**任一口径均不构成统计显著**。作为中立复核，本报告同时给出两种口径，避免选择性陈述。

### 3.2 异常数据点

1. **D4（批判性分析）两工具均偏低（opencode 5 / CodeBuddy 主评 5 / Hy3 重评 4）**：这是 5 维度中的**共同短板**，与模型能力（DSV4-Flash, AAI 40）相关，而非工具差异。说明在固定低-中能力模型下，批判性分析的不足是**模型瓶颈**，工具无法弥补。
2. **CodeBuddy 空文件**：2 个 `index.md` 因写入失败为 0 字节，被自评门禁捕获并修复。此属技术噪音，已排除，未影响评审分。
3. **Hy3 重评 D4 更低（4 vs 5）**：Hy3 给 CodeBuddy 的 D4 比 opencode 主评低 1 分，且 D5 高 1 分——反映**评审者风格差异**（Hy3 对批判性更严、对规范性更宽），属评审者间方差而非能力差异。
4. **【MiniMax-M3 新增观察：arXiv:2404.13501 主源引用差异】** 本复核通过 `grep -r "2404.13501" subjects/` 验证：
   - opencode 森林内 0 命中（`CodeBuddy_opencode.md` 评审中提及"主源缺失"属实）。
   - CodeBuddy 在 `subjects/CodeBuddy/forest/llm-agent-memory/index.md` line 8 的 `source` 字段中**有引用**：`source: "[综述] A Survey on the Memory Mechanism of LLM based Agents | arXiv:2404.13501"`。
   - 这一差异说明两工具在"主源归因完整性"上**存在 1 分质量差异**（CodeBuddy 优于 opencode），但 D2/D5 的评审分数并未显著拉开，**说明主源归因对综合分的影响被其他维度稀释**。

### 3.3 评审偏差影响评估

- **同源偏差（高风险）**：两个主评审者（CodeBuddy、opencode）共用底层模型 DSV4-Flash（AAI 40）。同源偏差客观存在，尤其在 D4/D5 主观维度。3 份评审的 `bias_risk` 均标 `low`，**但这低估了同源风险**——`low` 通常指"被评审者与评审者无利益关系"，并未量化"同源模型能力上限"带来的评审天花板。
- **Hy3 补充重评的作用与局限**：
  - **作用**：Hy3（不同家族）将 CodeBuddy 综合分从 6.2 拉到 6.8（含均值 6.5），方向上**降低**了同源视角的偏差。
  - **局限 1**（Hy3 未声明 AAI）：`reviews/opencode_CodeBuddy_Hy3.md` frontmatter 的 `reviewer_aai: "n/a (not AAI-rated)"` 表明 Hy3 未声明能力等级。AAI 差无法计算，软触发仲裁无法评估。**这是评审元数据的不完整项**。
  - **局限 2**（样本仍小）：样本仍只有 2 subject + CodeBuddy 仅 2 评审者 + opencode 仅 1 评审者，不改变"小样本 + 不对称评审"本质。
- **Hy3 草稿撰写者偏差**（中立复核重点）：
  - **方向 1**（自利抬高 CodeBuddy）：Hy3 草稿对 CodeBuddy 的 D4 解读为"评审者风格差异"——但 Hy3 自己也给 CodeBuddy D4=4（比 opencode 主评 5 低），**草稿并未借机抬高 CodeBuddy**。这与典型自利偏差模式不一致。
  - **方向 2**（自利贬低 opencode 提升 CodeBuddy）：Hy3 草稿未在文本中显著贬低 opencode 综合分（客观写 6.6），也未借补充重评强行拔高 CodeBuddy（含均值 6.5，仅 +0.3）。
  - **方向 3**（结论方向自利）：Hy3 草稿核心结论"工具差异 ≠ 质量差异"——这与"工具差异显著"的方向**正好相反**于自利者（参与者 Hy3 作为 CodeBuddy 评审者，理应倾向"CodeBuddy 显著更好"的结论）。
  - **【MiniMax-M3 中立判定】**：尽管存在自利偏差的形式风险，**Hy3 草稿的实际内容未呈现可观察的自利偏差**。其自报偏差风险的行为本身也降低了偏差概率（自报偏差者倾向于更自律）。但**样本量过小**（仅 2 subject）使任何方向性偏差的统计检验力不足，**不能完全排除"潜在偏差被样本噪声掩盖"的可能**。

### 3.4 元数据完整性与脚本可用性问题

- **共享脚本不兼容维度 2**：`collect_experiment_data.py` 为维度 1（不同模型）设计，对维度 2 存在 2 处不兼容：
  1. 文件名 glob 只扫 `review-*.md`，本实验报告命名 `{评审者}_{被评审者}.md`，匹配 0 份。
  2. 分组键按 `reviewee_model` 分组，维度 2 两工具模型同为 `DSV4-Flash`，会被错误合并。
  - 本次实验采用手动归集，但**未来维度 2/3 实验需修复脚本**（见 §5.3 待补充项）。
- **元数据不完整**：
  - CodeBuddy 的 `duration_minutes: 0`、`tokens_consumed: 0` —— 无法对比工具效率。

## 5. 结论与局限

### 5.1 可推广的结论

1. **工具差异 ≠ 质量差异（在本配置下）**：在固定 DSV4-Flash（AAI 40）+ 相同资料下，opencode 与 CodeBuddy 产出的森林综合质量无显著差异。
   - 按"全维度均值"口径：opencode 6.6 vs CodeBuddy 6.5，差 +0.1。
   - 按"综合分均值"口径：opencode 6.6 vs CodeBuddy 主评 6.2，差 +0.4。
   - 两口径均落在评审者间自然方差（±1）内。
2. **组织策略是工具带来的主要可观测差异**：opencode 倾向"统一森林"（1 森林 / 7 顶层目录 / 22 叶），CodeBuddy 倾向"按源分森林"（3 森林 / 11 树 / 64 叶）。这是方法论层面的**风格差异**，**不影响 D1-D5 内容质量评分**。
3. **模型能力是共同瓶颈**：D4（批判性分析）两工具均 ≤ 5 分，说明在 AAI 40 级别模型下，批判性分析不足是**模型上限问题，非工具问题**。
4. **【MiniMax-M3 新增：主源归因的微妙差异】** CodeBuddy 在 llm-agent-memory/index.md source 字段引用了 arXiv:2404.13501，opencode 森林全文 0 命中——这是两工具在"主源归因完整性"上**存在 1 个观测差异**，但**未在 D2/D5 评分上显著拉开**。该差异不构成推广性结论，但提示未来抽取时应**显式声明主源归因策略**。

### 5.2 局限（诚实声明）

| 局限 | 影响 |
|------|------|
| **样本量极小**（仅 2 subject，opencode 侧仅 1 位评审者） | 无统计显著性，所有差异结论置信度低 |
| **同源评审**（主评审者均 DSV4-Flash，AAI 40） | 系统性同源偏差无法完全排除；`bias_risk: low` 实际低估了同源风险 |
| **Hy3 未声明 AAI**（`reviewer_aai: n/a`） | 软触发仲裁无法评估；Hy3 评审数据的可比性受影响 |
| **撰写者非中立（Hy3 草稿）** | 自利偏差形式风险，**已由 MiniMax-M3 复核**；复核未发现可观察的偏差内容 |
| **维度 1 基线缺失** | 无法做跨维度对比，假说"工具差异 < 模型差异"未验证 |
| **元数据不完整**（CodeBuddy 效率/版本、Hy3 AAI） | 效率对比不可行，仲裁触发判定不可行 |
| **数据归集为手动**（脚本不兼容维度 2） | 评分提取依赖人工，已记录脚本 bug，待修 |
| **Hy3 草稿存在事实错误**（CodeBuddy 71 文档 vs 实际 66） | 已由 MiniMax-M3 复核修正 |
| **CodeBuddy 元数据声明与实际不符**（`total_documents: 71` vs 实际 66） | 需修正元数据或在文档生成脚本中排查 |

### 5.3 待补充实验 / 后续建议

1. **【高】修复共享脚本**：`collect_experiment_data.py` 需支持维度 2/3（文件名 glob + 按 `reviewee_tool` 分组），见 `results/comparison-matrix-tools.md` 文末说明。
