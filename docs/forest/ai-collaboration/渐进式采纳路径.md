# 渐进式采纳路径

## 总览

```
阶段 1：单 Agent 辅助     阶段 2：知识引擎上线    阶段 3：多 Agent 协作     阶段 4：自运转组织
──────────────────────────────────────────────────────────────────────────────────→
  1-2 周                  2-4 周                 4-8 周                   持续迭代
```

## 阶段 1：单 Agent 辅助（1-2 周）

**目标**：建立与单个 AI Agent 的有效协作习惯。

### 具体动作
1. 选定一个主力编码 Agent（Codex / Claude Code / OpenCode）
2. 将所有任务通过**聊天界面**发出，定义为目标而非实现指令
3. 每天结束时花 15 分钟记录：哪些任务适合委托、哪些不适合
4. 关闭 IDE 的逐行 diff 审查习惯，改为只看最终结果

### 里程碑
- ✅ 能连续 3 天不以"写代码"方式完成任务
- ✅ 整理出一份"适合委托的任务清单"和"不适合委托的任务清单"
- ✅ System Prompt 从"塞满所有信息"精简到 < 2,000 Token

### 回退条件
- 如果连续 3 个任务 Agent 产出完全不可用 → 回退到传统方式，分析原因后再试

## 阶段 2：知识引擎上线（2-4 周）

**目标**：搭建元知识引擎 MVP，让 Agent 能按需检索领域知识。

### 具体动作
1. 搭建 SQLite + sqlite-vec 基础设施（参见 [技术选型对比](../meta-knowledge-engine/技术选型对比.md)）
2. 将现有文档按森林理论整理为知识原子（参见 [知识原子规范](../meta-knowledge-engine/知识原子规范.md)）
3. 实现 `retrieve(query)` 函数，验证"层级定位 + 向量匹配 + 图追溯"优于纯向量检索
4. 将检索结果拼接入 Agent 上下文，替代超长 System Prompt

### 里程碑
- ✅ 至少 1 个森林有完整的 树→枝干→叶 层级结构
- ✅ `retrieve(query)` 的 Top-5 召回相关性 > 0.8（人工评估）
- ✅ Agent 在知识检索辅助下，能回答此前需要人类解释的领域问题

## 阶段 3：多 Agent 协作（4-8 周）

**目标**：引入 Manager Agent，实现多 Worker 并行协作。

### 具体动作
1. 实现 Manager Agent 的任务拆解与调度逻辑（参见 [Agent角色与职责定义](Agent角色与职责定义.md)）
2. 至少设置 2 个不同专长的 Worker Agent（code-writer + test-writer）
3. 实现 Reviewer Agent 的自动门禁（编译/Lint/测试覆盖率）
4. 建立胶水提示词模板，确保 Agent 间通信清晰（参见 [胶水提示词设计](胶水提示词设计.md)）

### 里程碑
- ✅ Manager Agent 能成功将 1 个 Epic 拆解为 ≥ 3 个子任务
- ✅ 多 Worker 并行执行的总耗时 < 单 Worker 串行执行
- ✅ Reviewer 自动门禁通过了至少 5 个真实 PR

### 注意
- 此阶段引入的并行度可能带来**产出冲突**（多 Worker 修改同一文件）——这是正常的
- Manager 的冲突检测和上报机制是此阶段的核心验收点

## 阶段 4：自运转组织（持续迭代）

**目标**：Agent 团队日常自运转，人类只在关键决策点介入。

### 具体动作
1. 引入事件驱动：Git Push / Issue 创建 / Cron 定时 → 自动唤醒 Manager
2. 完善记忆回灌：高频引用叶子自动提升权重，用户修正覆盖原始文档
3. 建立 Agent 表现的量化仪表盘（任务完成率、平均耗时、人工介入频率）
4. 持续扩充知识森林（新项目/新领域文档接入）

### 里程碑
- ✅ Manager Agent 能在无人工触发的情况下主动处理 ≥ 80% 的常规任务
- ✅ 人工每天介入 < 3 次
- ✅ 知识森林覆盖 ≥ 3 个独立领域

### 永不自动化的事项
- 架构方向决策
- 安全策略变更
- 用户数据处理规则修改
- 上线审批
