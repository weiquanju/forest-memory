# 技术选型对比

## 存储引擎对比

| 维度 | SQLite + 扩展 | Neo4j | Milvus | ChromaDB |
|------|-------------|-------|--------|----------|
| **图遍历** | ✅ 邻接表 + 递归 CTE | ✅ 原生图数据库 | ❌ 不适用 | ❌ 不适用 |
| **向量检索** | ✅ sqlite-vec / sqlite-vss | ⚠️ 需额外组件 | ✅ 原生向量检索 | ✅ 原生向量检索 |
| **全文搜索** | ✅ FTS5 (BM25) | ⚠️ 需插件 | ❌ 不适用 | ❌ 不适用 |
| **部署复杂度** | ✅ 零依赖单文件 | ❌ JVM + 独立服务 | ❌ 独立服务 | ⚠️ Python 进程 |
| **数据迁移** | ✅ 复制一个文件 | ❌ 需 dump/restore | ❌ 需工具 | ⚠️ 需工具 |
| **个人使用** | ✅ 天然适合 | ❌ 过重 | ❌ 过重 | ⚠️ 可接受 |
| **资源占用** | < 50MB 内存 | > 1GB 内存 | > 2GB 内存 | > 500MB 内存 |
| **查询灵活性** | ✅ 完整 SQL | ⚠️ Cypher 学习成本 | ⚠️ 受限 | ⚠️ 受限 |

## 决策矩阵

### SQLite 胜出场景（个人开发者 / 小团队）
- 知识原子 < 10 万条
- 单机部署，无分布式需求
- 需要 SQL 进行复杂关联查询
- 数据备份 = 文件拷贝
- **结论：元知识引擎 MVP 的最优选择**

### Neo4j 适用场景
- 图关系极度复杂（百万级别节点 + 深层遍历）
- 团队有 Cypher 和 JVM 运维经验
- 需要可视化图浏览
- **但 MVP 阶段不建议**——SQLite 递归 CTE 已足够覆盖知识领域的图遍历

### Milvus / ChromaDB 适用场景
- 纯向量检索，亿级向量
- 不需要图关系遍历
- 有独立运维能力
- **但元知识引擎的核心差异点是"层级图 + 向量 + 关键词"三合一**，纯向量数据库反而割裂了检索能力

## 推荐技术栈（MVP）

```
┌─────────────────────────────────────────┐
│  Python 3.11+                           │
│  ├── sqlite-vec     (向量检索)           │
│  ├── openai / anthropic (LLM 抽取)       │
│  ├── tree-sitter    (代码 AST 解析)      │
│  ├── markdown-it-py (文档解析)           │
│  └── sentence-transformers (本地嵌入，可选)│
└─────────────────────────────────────────┘
```

## 升级路径

当 SQLite 单文件方案遇到瓶颈时：

```
单文件 SQLite
    │  知识原子 > 10w 或查询延迟 > 500ms
    ▼
SQLite + ChromaDB（向量分离）
    │  图遍历深度 > 5 跳或节点 > 100w
    ▼
SQLite（关系 + 全文）+ Neo4j（图）+ Milvus（向量）
```

但在 MVP 阶段和可预见的个人使用场景中，单文件 SQLite 完全足够。
