# 跨森林知识注入与架构细化

## 概述

本文档从三个支撑森林中抽取可应用于 MKE 设计与实现的知识点，并按五层架构逐层细化。每一层先呈现**知识注入点**（来自哪个森林、哪片叶子的什么洞见），再给出**架构细化建议**。

```
frs (学术对标) ──→ 方法论验证 + 前沿方向指引
bim (生物学启发) ──→ 设计原理 + 算法启发
aic (消费场景) ──→ 使用约束 + 输出格式 + 验证反馈
                        │
                        ▼
              ┌─────────────────┐
              │  MKE 五层架构   │
              │  逐层细化       │
              └─────────────────┘
```

## 边界声明（"MKE 不做什么"）

边界声明已提取为独立知识原子，参见 [项目定位与边界声明](项目定位与边界声明.md)。

每一条细化建议必须在边界内——如果一项建议在边界上模糊，应明确收紧其职责范围。

## 第一层：数据接入与归一化层

### 知识注入点

| 来源 | 知识点 | 注入内容 |
|------|--------|---------|
| bim / 模块化记忆分类 | 四类记忆的脑区分工——情景/语义/程序/工作记忆 | MKE 的知识原子目前只覆盖语义记忆（Leaf），缺少对程序性记忆（Prompt模板/规则）和工作记忆的结构化收纳 |
| frs / Agent 记忆三维分类 | 载体形式：Token级（显式）/ 参数级（隐式）/ 潜在级（隐状态） | MKE 当前仅覆盖 Token 级显式知识，未来可扩展收纳参数级经验（LoRA权重/模型微调产生的知识） |
| bim / BTSP 单次学习 | 秒级窗口一次性增强所有活跃突触 | 高显著性知识（用户明确修正、架构决策）应作为"一次写入"高优先级直接入库 |

### 架构细化

**1.1 知识原子类型扩展**

在 YAML Frontmatter 中增加 `atom_type` 字段：

```yaml
atom_type: semantic    # 语义知识（默认，对应 Leaf）
# 或
atom_type: procedural  # 程序性知识（Prompt 模板、调度规则、胶水提示词）
# 或
atom_type: episodic    # 情景知识（Interaction_Memory 中固化的交互模式）
```

- `semantic`：客观领域事实——当前 Leaf 表覆盖
- `procedural`：Agent 行为规则——新增，建议存入 `Procedure` 表或复用 Leaf 表的 `status='stable'` + `atom_type='procedural'`
- `episodic`：从 Interaction_Memory 中提炼的交互经验模式——当前 `pattern` 字段的结构化升级

**1.2 写入优先级分层**

借鉴 BTSP 的"一次写入"机制，将知识写入分为三个优先级：

| 优先级 | 触发条件 | 入库路径 |
|--------|---------|---------|
| P0（即时写入） | 用户明确修正 / 架构决策 | 跳过 LLM 抽取器，直接创建 Leaf |
| P1（批量写入） | 新文档接入 / 代码 AST 扫描 | 标准 LLM 抽取器流程 |
| P2（离线巩固） | 高频引用 + 无修正的交互模式 | 离线定时任务从 Interaction_Memory 提取为 Leaf |

## 第二层：知识构建与图索引层

### 知识注入点

| 来源 | 知识点 | 注入内容 |
|------|--------|---------|
| bim / CLS 互补学习系统 | VAE（新皮层/泛化）+ MHN（海马体/特化）→ ~90% 持续学习准确率 | MKE 的"快速层(Interaction_Memory) + 慢速层(Leaf)"之间需要自动化的"巩固管道"——当前仅靠个性化 PageRank 单向提升权重 |
| bim / KV 键值记忆框架 | 海马体编码"键"（索引）、新皮层存储"值"（内容），遗忘主因是检索失败而非擦除 | References 表 = 键之间的关联路径；向量嵌入 = 键的数学表示。设计原则：永不删除 Leaf，仅通过 status 和权重管理可访问性 |
| frs / 知识编辑 | PRUNE 条件数约束 → 知识更新时需保护已知正确知识；逻辑编辑 24% 差距 → 修改一处必须级联检测 | References 表需增加 `cascade_on_update` 标记——哪些引用方在源 Leaf 变更时需强制校验 |
| frs / GraphRAG 实用化 | RRF 融合向量相似度与图遍历，实体/文档/关系独立嵌入向量，多粒度匹配提升 15% | 当前 Vectors 表仅对 Leaf 正文做嵌入，建议增三张嵌入表：叶子正文嵌入 / 关键字嵌入 / 引用关系嵌入 |

### 架构细化

**2.1 自动化巩固管道**

在第二层增加 **Consolidation Pipeline**（巩固管道），连接 Interaction_Memory（快速层）与 Leaf 表（慢速层）：

```
Interaction_Memory（快速层）
        │
        ▼  离线定时任务（每日/每 N 轮对话）
┌───────────────────────────┐
│  Consolidation Pipeline   │
│                           │
│  1. 扫描：高频引用 + 无修正 + 高评分 (rating≥4) 的交互模式
│  2. 提取：LLM 从 Interactions 中提取可泛化的知识模式
│  3. 去重：与现有 Leaf 做交叉声明检测
│  4. 入库：创建新 Leaf（或更新已有 Leaf）
│  5. 关联：建立 Interaction_Memory → Leaf 的巩固来源追溯
└───────────────────────────┘
        │
        ▼
   Leaf 表（慢速层）
```

这一管道对应以下生物学机制的工程实现：
- **海马→皮层系统巩固（CLS）**：快速层→慢速层的知识转移
- **SWR 选择性重放**：按频率/评分筛选，非全量巩固
- **睡眠巩固**：离线定时，不影响在线服务

**职责边界**：Consolidation Pipeline 是**知识质量治理的"来源管理"**——确保从交互中提取的知识经过交叉声明检测和质量门禁才入库。它不做：
- ❌ 大规模交互日志的 ETL 处理（那是 Spark/Ray 的事）
- ❌ 通用经验抽取/模式挖掘（那是 ML Pipeline 的事）
- ✅ 只处理**已通过质量筛选（高频+高评分+无修正）的交互**，提取为知识原子并校验

**2.2 永不删除原则**

遵循 KV 框架的"检索失败而非记忆擦除"原则：

- `status` 字段仅降级为 `deprecated`，不物理删除
- 权重衰减≠数据擦除——知识还在，只是检索路径被遮蔽
- 沉降印迹可被"再激活"——若新的交互模式重新引用已弃用 Leaf，自动提升权重

**2.3 引用图谱增强**

在 `References` 表中增加字段：

```sql
ALTER TABLE reference ADD COLUMN cascade_on_update BOOLEAN DEFAULT FALSE;
-- TRUE: 当 to_leaf_id 变更时，from_leaf_id 需要级联校验

ALTER TABLE reference ADD COLUMN temporal_rel TEXT;
-- 'before', 'after', 'during' —— 支持 DYNA 式的时态关系
-- 用于情景记忆：A事件发生在B事件之前
```

**2.4 多粒度向量嵌入**

当前仅对 Leaf 正文做嵌入。建议增加三张嵌入表，对应实用级 GraphRAG 的多粒度匹配策略：

```sql
-- 叶子正文嵌入（已有，vec_leaf）
-- 关键字嵌入（新增）
CREATE VIRTUAL TABLE IF NOT EXISTS vec_keyword USING vec0(
    leaf_id  TEXT PRIMARY KEY,
    embedding FLOAT[768]
);

-- 引用关系嵌入（新增）—— 捕获"from→to"的语义
CREATE VIRTUAL TABLE IF NOT EXISTS vec_ref USING vec0(
    ref_id   INTEGER PRIMARY KEY,
    embedding FLOAT[768]
);
```

检索时通过 RRF（倒数排名融合）综合三路信号——提升最高 15% 的检索质量（与实用级 GraphRAG 一致）。

## 第三层：混合检索引擎层

### 知识注入点

| 来源 | 知识点 | 注入内容 |
|------|--------|---------|
| frs / ToG/PoG/SoG | LLM⊗KG beam search 探索推理路径、知识可追溯性 | MKE 当前仅 1-hop 图扩散，可扩展为 k-hop beam search 多跳探索，每步可回溯到参考 Leaf |
| frs / CS-RAG | 不完美 KG 的充分性检查——原子约束规划识别伪噪声和检索漂移 | MKE 第三阶段"裁决与迭代"可引入约束规划：不仅问"缺什么"，还要验证"已有的对当前问题是否充分" |
| frs / RLVR 校准退化 | LLM 自评不可靠——答案错误时仍给出极高置信度 | MKE 裁决环节不能仅依赖 LLM 单次自评。应引入规则锚点（Rule Anchor）：对关键类型的信息缺失设置硬性检查 |
| bim / 模式完成 | CA3 吸引子网络——从部分线索恢复到完整记忆 | MKE 渐进式检索的图扩散 = 模式完成的工程实现，可深化为 multi-hop attractor retrieval |
| bim / 联想记忆与内容寻址 | KV 框架统一了 CAM 与 Transformer 的 Q-K-V 机制 | MKE 当前检索仅用向量余弦作为相似度，可增加 Q-K-V 范式：Q=查询嵌入、K=Leaf 向量、V=Leaf 正文 |
| aic / 注意力瓶颈 | 上下文窗口 = 注意力资源，瓶颈已从 Token→算力→注意力 | 70% 阈值可细化为按 Worker 角色分配：code-writer 需要精确 API（高精度低数量）vs researcher 需要概览（低精度高数量） |

### 架构细化

**3.1 五阶段渐进式检索（从四阶段升级）**

```
阶段一：多路粗筛（向量 + 关键词 + 层级）
  ├─ 向量语义匹配：Top K 候选（sqlite-vec）
  ├─ BM25 关键词匹配：Top K' 候选（FTS5）
  ├─ 层级定位：先匹配森林→树，再下钻枝干
  └─ RRF 融合 → Top M 候选叶子

阶段二：多跳图扩散（k-hop beam search）
  ├─ 从 Top M 候选出发
  ├─ 沿 References 表做 k-hop 扩散（k=1-3，beam width=5）
  ├─ 每跳记录溯源路径（Leaf A → ref → Leaf B → ref → Leaf C）
  └─ 目的：从"语义相似"扩展到"关系相关"+"因果关联"

阶段三：约束规划裁决（从 LLM 自评升级）
  ├─ 规则锚点：对关键信息类型设置硬性检查
  │   - 如查询涉及"配置参数"→必须检索到至少 1 个 config 类型 Leaf
  │   - 如查询涉及"时间顺序"→必须有 temporal_rel 引用链
  ├─ LLM 裁决：评估已收集知识对当前问题的充分性
  │   - 输出：{sufficient: bool, missing_categories: [], confidence: 0-1}
  └─ 双判据：规则锚点 × LLM 裁决 → 只有两者都满足时才停止迭代

阶段四：窗口防溢出（保持）
  ├─ Token_Counter 监控
  ├─ 70% 阈值触发摘要压缩
  └─ 压缩等级按 Worker 角色可配置

阶段五：知识可追溯输出（新增）
  ├─ 每条检索结果附带溯源路径
  └─ 格式：{leaf_id, content, trace: [leaf_A, ref_type, leaf_B, ...]}
  └─ 若 Agent 在推理中使用该知识，可回溯到原始 Leaf 验证
```

**3.2 校准退化防护**

裁决阶段的硬性设计原则：
- **不依赖 LLM 单次自评**——RLVR 训练可能产生校准退化的模型
- **规则锚点 + LLM 裁决**双重判定
- 规则锚点是领域专家可配置的检索完备性检查规则
- 若 LLM 裁决与规则锚点冲突 → 优先信任规则锚点，但同时记录冲突日志供后续分析

**3.3 知识消费配置接口（按消费方角色）**

借鉴 aic 中 "不同 Worker 类型需要不同粒度的知识" 的洞见。**注意职责边界**：MKE 不管理 Agent 行为（那是 LangChain/Dify 的事），MKE 仅定义**知识输出粒度配置**——消费方告诉 MKE "我需要什么精度的知识"，MKE 按需返回。Agent 的调度、任务拆解、对话管理均在 MKE 外部。

| 消费场景 | 检索模式 | K 值 | Hop 数 | 窗口阈值 | 压缩策略 |
|---------|---------|------|--------|---------|---------|
| 精确编码场景 | 精确 | Top 5 | 1-hop | 50% | 不压缩（精确优先） |
| 调研概览场景 | 概览 | Top 20 | 3-hop | 80% | 激进压缩 |
| 因果排查场景 | 因果 | Top 10 | 2-hop | 70% | 按时间序保留 |
| 边界条件场景 | 边界 | Top 8 | 1-hop | 60% | 边界案例优先 |

这些是由消费方在调用 `retrieve(query, profile="precise"|"overview"|"causal"|"boundary")` 时指定的**知识消费 profile**，不与特定 Agent 角色绑定。

**3.4 互补接口：结构化检索输出格式（新增）**

> **注入来源**：aic / 注意力瓶颈与价值导向 + 开放生态与模型路由——"可插拔的 Agent 技术栈"要求 MKE 定义标准化接口，供 Dify/LangChain/LlamaIndex 等框架作为知识质量治理层消费。

MKE 作为 RAG 生态中的"知识供给侧质量治理层"，需要定义清晰的**消费接口**：

```json
// retrieve(query, profile) 的标准输出格式
{
  "query": "JWT Token 过期后的刷新逻辑",
  "profile": "precise",
  "results": [
    {
      "leaf_id": "mke:元知识引擎:存储设计:SQLite表结构设计",
      "content": "...",
      "relevance_score": 0.92,       // RRF 融合分数
      "confidence": 0.87,            // 知识可信度（基于 status + 引用频次 + 修正历史）
      "trace": [                     // 可追溯溯源路径
        {"leaf_id": "...", "ref_type": "config", "hop": 0},
        {"leaf_id": "...", "ref_type": "depends", "hop": 1}
      ],
      "status": "stable",
      "quality_alerts": []           // 若有冲突/待修正，在此标注
    }
  ],
  "retrieval_meta": {
    "total_candidates": 5,
    "iterations": 2,                 // 裁决迭代次数
    "window_used_pct": 42,           // 上下文窗口占用百分比
    "rule_anchors_checked": ["config_param_present"],
    "rule_anchors_failed": []
  }
}
```

**互补关系定义**：

| 框架 | MKE 的角色 | MKE 不做的事 |
|------|-----------|-------------|
| **Dify** | 作为 Dify 知识库的"质量治理前置层"——文档先经 MKE 组织/校验/版本化，再导入 Dify 做 RAG | 不做 Dify 的 chunk 分割、对话编排、工作流 |
| **LangChain** | 作为 LangChain 的 `BaseRetriever` 实现——通过标准化检索接口注入质量校验过的知识 | 不做 LangChain 的 Chain/Agent/Tool 编排 |
| **LlamaIndex** | 作为 LlamaIndex 的 `CustomRetriever`——提供层级化+图引用的混合检索 | 不做 LlamaIndex 的 ingestion pipeline、index 构建 |

**与 aic/模型路由的关系**：不同消费方（Dify pipeline vs LangChain agent vs 直接 LLM）通过 `profile` 参数获取不同粒度的知识输出，MKE 不感知消费方的内部逻辑。

## 第四层：持久化与记忆融合层

### 知识注入点

| 来源 | 知识点 | 注入内容 |
|------|--------|---------|
| bim / 记忆再巩固 | 提取→不稳定窗口→修改→重新稳定 | `user_correction` 覆盖原始知识 = 再巩固的工程实现。可深化为：修正不仅覆盖当前回答，还触发关联 Leaf 的级联复核 |
| bim / 资源竞争 + 主动遗忘 | 写入即覆盖（被动）+ Rac1 主动遗忘通路（权重衰减/剪枝） | MKE 缺少系统性容量管理——当前只有 Token 防溢出，没有 Leaf 级别的衰减和淘汰机制 |
| bim / 情感显著性 | 杏仁核去甲肾上腺素→高情感显著性的存储优先级 | `rating` 字段应从"记录"升级为"驱动"——影响存储优先级、检索权重、巩固概率 |
| bim / RL 驱动的记忆管理 | Mem-α 通过 RL 自主学习存储/更新/检索策略 | `rating` 可作为 RL 奖励信号，自适应调整记忆策略，而不依赖人工固定阈值 |
| frs / MemVerse 双区 | 短期+长期双区 + 持续巩固 + 周期蒸馏 | MKE 缺少"周期蒸馏"机制——将长程记忆关键知识压缩为参数化记忆 |
| frs / 经验跟随风险 | 经验跟随可能导致错误累积 | 检索结果应附带"可信度 Score"，高经验跟随但低评分的历史模式应降权 |
| aic / CEO-子公司模型 | Worker 需要领域知识上下文注入 | Interaction_Memory 应支持按 Worker 角色过滤——不同 Worker 的"经验回灌"范围不同 |

### 架构细化

**4.1 四类记忆的 MKE 实现架构**

| 记忆类型 | MKE 实现 | 存储 | 生命周期 |
|---------|---------|------|---------|
| **情景记忆** (Episodic) | `Interaction_Memory` 表 | SQLite row | 创建→引用→评分→可能巩固为语义记忆 |
| **语义记忆** (Semantic) | `Leaf` 表 + 向量嵌入 | SQLite + sqlite-vec | draft→reviewed→stable→deprecated |
| **程序性记忆** (Procedural) | Prompt 模板 / 规则配置 | 文件系统或 Leaf (atom_type=procedural) | 版本控制，可被 Agent 直接加载 |
| **工作记忆** (Working) | 滑动窗口缓存（最近 N 轮对话） | 内存/Redis | 会话级，窗口满时 FIFO 或按重要性淘汰 |

对标 MemVerse 的"双区+蒸馏"架构：
- **短期区**：Working Memory（滑动窗口缓存）
- **长期区**：Episodic (Interaction_Memory) + Semantic (Leaf)
- **蒸馏（缺失）**：需新增"周期巩固"任务——将长程交互模式蒸馏为 Semantic Leaf

**4.2 容量管理四机制**

借鉴大脑的三层遗忘机制，建立 MKE 的系统容量管理：

| 机制 | 生物对应 | 工程实现 |
|------|---------|---------|
| **被动竞争** (写入即覆盖) | 突触资源竞争 | 有限的 Token 窗口 + 旧知识摘要压缩 |
| **主动衰减** (权重自然降低) | Rac1-Cofilin 通路 | 个性化 PageRank 权重按时间衰减（半衰期可配置） |
| **显著性保护** (重要记忆保护) | 杏仁核去甲肾上腺素 | `rating≥4` 或 `user_correction` 标记的 Leaf 免于衰减 |
| **检索失敗** (非擦除) | 沉默印迹 | `status='deprecated'` 不删除，仅权重降至检索阈值以下，可被重新激活 |

**4.3 自适应记忆策略（RL-Driven）**

借鉴 Mem-α 的 RL 驱动思想，在 `Interaction_Memory` 的 `rating` 字段基础上：

```
Interaction → rating（人工信号）
                    ↓
          个性化 PageRank 权重调整
                    ↓
          高频引用 + 高评分 → 触发 Consolidation Pipeline
          低频引用 + 低评分 → 权重衰减
          高频引用 + 低评分（错误但常用）→ 标记为"待修正"，提升审核优先级
```

未来可升级为真正的 RL 策略（当前 MVP 阶段使用规则阈值即可）。

**4.4 跨 Worker 记忆共享**

借鉴 SoHip 的多智能体共享记忆机制：

```
                    ┌──────────────────────┐
                    │   共享 Leaf 表         │
                    │   (集体语义记忆)        │
                    └──────┬───────────────┘
                           │ 所有 Worker 可读
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
   ┌────────────┐  ┌────────────┐  ┌────────────┐
   │ Worker A   │  │ Worker B   │  │ Worker C   │
   │ IM_A       │  │ IM_B       │  │ IM_C       │
   │ (个体经验)  │  │ (个体经验)  │  │ (个体经验)  │
   └────────────┘  └────────────┘  └────────────┘
   
   IM_X = 该 Worker 私有的 Interaction_Memory 记录
```

- 共享 Leaf 表 = "集体知识"（所有 Worker 检索同一份语义记忆）
- 个体 Interaction_Memory = "个体经验"（Worker 从自己的成功/失败中学习）
- 个体经验可通过 Consolidation Pipeline 贡献回集体 Leaf 表（需人工审核）

### 架构细化

**5.1 三层冲突检测升级**

从当前单一的"交叉声明检测"升级为三层：

```
第一层：声明一致性（已有）
  └─ 两文档是否重复声明同一知识点
  └─ 实现：向量相似度 + LLM 判断 → 拒绝写入 + 引用建议

第二层：逻辑一致性（新增）
  └─ 修改 Leaf A 时，其引用方 Leaf B/C/... 的陈述与 A 的新内容是否矛盾
  └─ 触发：cascade_on_update=true 的引用方自动进入复核队列
  └─ 实现：对每个引用方，LLM 逐条验证其内容与新 Leaf A 的一致性
  └─ 对标：逻辑规则编辑的 24% 差距问题

第三层：系统一致性（新增）
  └─ 定期全量扫描：检测全局知识冲突（对标 ConflictBank 的记忆内冲突）
  └─ 实现：对语义相近的 Leaf 做 pairwise 一致性检查（抽样，非全量 O(n²)）
  └─ 输出：冲突报告 + 建议修正方向
```

**5.2 治理自动化 vs 人工审核**

借鉴 ConflictBank 的"人在回路验证成本降低"策略：

| 治理动作 | 自动化程度 | 人工介入条件 |
|---------|-----------|-------------|
| 交叉声明检测 | 全自动 | 向量相似 0.85-0.95 区间需要人工裁决 |
| 级联一致性校验 | 全自动检测 | 仅上报冲突（`severity='critical'`），人工决定修正方向 |
| 系统一致性扫描 | 自动抽样 | 异常检测 + 抽样审核（而非全量人工审核） |
| 死链检测 | 全自动 | 自动报告，人工确认删除/归档 |
| 版本快照 | 全自动 | 人工触发回退 |

**5.3 知识原子生命周期管理**

| 状态 | 含义 | 检索可见 | 写入权限 | 转移条件 |
|------|------|---------|---------|---------|
| `draft` | 初建，未经审核 | 需要显式指定 | LLM 抽取器 | 人工审核通过 → `reviewed` |
| `reviewed` | 已审核，可检索 | 是 | 人工 | 稳定使用 ≥ 3 次交互 → `stable` |
| `stable` | 稳定知识 | 是（高权重） | 人工（需级联校验） | 内容过时 → `deprecated` |
| `deprecated` | 已弃用 | 否（除非追溯） | 无 | 若重新被引用 → `reviewed`（再激活） |

**5.4 MKE 自评估体系**

借鉴 MemoryArena/LifelongAgentBench 的评估范式，建立 MKE 的三个量化指标：

| 指标 | 定义 | 测量方法 | 目标 |
|------|------|---------|------|
| **检索精准率** | Top-K 结果中与查询相关的比例 | 人工标注 100 条查询，计算 Precision@5 | > 0.80 |
| **多跳完整性** | 多步推理所需知识的覆盖度 | Scheherazade 式长链推理问题，检测信息是否完整 | > 0.75 |
| **冲突检测召回** | 已知冲突中被自动检测的比例 | 人工注入 20 个已知冲突，检测自动化检出率 | > 0.90 |

**5.5 运行时可观测性指标（新增）**

> **注入来源**：frs / 推理评估基准演进 + aic / 协作反模式清单——"上下文过载"和"知识不一致"是两大反模式信号，MKE 应在运行时暴露这些指标供外部监控系统消费。

除了离线评估指标，MKE 应在运行时导出以下 metrics：

| 指标类别 | 具体指标 | 用途 | 告警阈值建议 |
|---------|---------|------|-------------|
| **检索质量** | `retrieval_window_avg_pct` | 监控检索窗口利用率，防止频繁溢出 | > 70% 触发告警 |
| **检索质量** | `iteration_count_p99` | 裁决迭代次数——过高说明一次检索难以满足 | > 5 次触发告警 |
| **治理健康** | `conflict_detection_count_daily` | 每日检测到的冲突数量 | 突增 > 200% 触发告警 |
| **治理健康** | `cascade_impact_leaf_count` | 单次变更影响的级联 Leaf 数量 | > 10 需人工复核 |
| **知识演化** | `deprecated_leaf_count` vs `total_leaf_count` | 知识腐化率 | > 20% 需批量清理审核 |
| **知识演化** | `consolidation_candidate_count_daily` | 每日可巩固的交互模式数 | 连续多日为 0 → 交互质量可能下降 |
| **消费质量** | `anchor_rule_fail_count` | 规则锚点未通过的检索次数 | > 10% 检索触发 → 知识库可能存在盲区 |

导出方式：通过结构化日志（JSON lines）或 Prometheus metrics endpoint，不绑定特定监控栈。

12. 三层冲突检测（L2 逻辑一致性 + L3 系统一致性）
13. MKE 自评估体系（Precision@5 / 多跳完整性 / 冲突召回）
14. 跨 Worker 记忆共享
15. 知识消费 profile 接口（按场景的检索模式）

### 永不纳入 MKE 的事项（边界保护）
- ❌ Agent 调度逻辑（任务拆解、Worker 分配、对话管理）→ 归 aic/Manager Agent
- ❌ 原始文档的格式转换（pdf→md、图片 OCR 等）→ 用外部工具预处理
- ❌ 大规模日志 ETL → 归 Spark/Ray
- ❌ 向量数据库集群管理 → 单文件 SQLite + sqlite-vec 足够
