# 渐进式检索引擎

## 问题定义

检索领域知识的核心矛盾：

| 策略 | 优势 | 劣势 |
|------|------|------|
| **精准** | 只取最相关 3-5 个节点，Token 开销小 | 可能遗漏关键信息 |
| **完整** | 取整个子树，信息不遗漏 | 可能超出上下文窗口 |

**解决方案**：渐进式检索（Iterative Retrieval）——先粗召回一批候选节点，让 LLM 判断是否足够，不够则继续扩展。

## 四阶段检索流程

### 阶段一：粗筛（向量相似）

- 根据用户问题，在 `sqlite-vec` 向量表中召回 **Top 5-10** 个最相关的叶子节点
- 使用余弦相似度或欧几里得距离进行语义匹配
- **建议补充**：增加 FTS5（SQLite 全文搜索）做 BM25 关键词匹配，解决纯向量检索的"语义漂移"问题

### 阶段二：图扩散（引用追溯）

- 获取 Top 5-10 叶子的 `Leaf_ID`
- 在 `References` 引用图谱中执行 **1 跳（1-hop）扩展**
- 拉取被高频引用的"父级枝干"或"标准 M 定义"等关联节点
- 目的：向量只能找"语义相似"的，图关系能找"关系相关"的（如"JWT 过期后 Refresh Token 刷新逻辑受哪些配置影响"）

### 阶段三：裁决与迭代

- 将当前收集到的所有文本注入 LLM
- 问一句：**"基于现有背景，能回答用户问题吗？缺什么类型的信息？"**
- 若不满足：LLM 输出缺失的森林/树标签，引擎据此再走一次向量检索
- 循环执行，类似 SQL 中的递归 CTE，直到 LLM 判断信息充足

### 阶段四：窗口防溢出

- 每次循环携带 `Token_Counter`
- 当累计超过上下文阈值（如 70%）时暂停扩散
- 启动**摘要压缩**：将最不相关的枝干叶子合并为一句话
- 腾出空间后继续检索

## 检索能力对照

| 检索能力 | 实现方式 |
|---------|---------|
| 向量语义搜索 | sqlite-vec 余弦相似度 |
| 图关系遍历 | References 表 + 1-hop 扩散 |
| 关键词匹配 | 建议补充 SQLite FTS5（BM25） |
| 时序过滤 | Content_Hash + Epoch_ID |
| 渐进式迭代 | LLM 裁决 + 递归循环 |

## 与纯向量检索的对比

纯向量检索的局限：只能找"语义相似"的，无法找"关系相关"的。

森林理论的三段式检索优势：**层级做粗筛→图关系做精筛→向量做语义匹配**，这是混合检索（Hybrid Retrieval）的经典范式，与当前 GraphRAG 的技术方向一致。
