# MKE 在 LLM 会话拼图中的位置

## 核心定位

**MKE 不是修改 LLM 架构，而是给 LLM 加一个外挂的知识治理层。**

它承认 LLM 的无状态本质不改变——参数仍然冻结，上下文窗口仍然有限——但在"LLM 之外"建立一套机制，确保每次 LLM 打开新对话时，可以通过检索访问到持久化且经过质量治理的知识。

## MKE 弥补了哪部分

```
LLM 会话机制的局限 → MKE 的对应方案：

无状态（对话间无记忆）
  → MKE Layer 4：Interaction_Memory 表 + 记忆回灌 + Consolidation Pipeline
  → 跨对话的知识被持久化，LLM 下轮通过检索获取

上下文窗口有限
  → MKE Layer 3：渐进式检索——"先定位森林，再下钻叶子"
  → 只注入与当前问题最相关的知识，而非全量灌输

知识可能冲突
  → MKE Layer 5 + Layer 2：SSOT + 三层冲突检测
  → 建库时消灭交叉声明；运行时检测逻辑冲突

知识可能过时
  → MKE Layer 5：生命周期管理（draft→reviewed→stable→deprecated→再激活）
  → 永不删除原则——过时知识保留但标记状态，支持知识演化史追溯

知识无法溯源
  → MKE Layer 2 + 5：refs 引用链 + source_count + provenance chain
  → 每条知识原子可以追溯到原始来源和抽取模型
```

## MKE 不碰的

| LLM 会话局限 | MKE 不解决的原因 |
|-------------|---------------|
| 注意力机制的 O(n²) 代价 | 这是 Transformer 架构的内生问题，MKE 是外挂层 |
| 幻觉（LLM 凭空编造） | 这是 LLM 推理能力问题，MKE 只能确保注入的知识是对的，不能确保 LLM 正确使用它 |
| 推理偏差（LLM 的逻辑错误） | MKE 管知识质量，不管推理质量 |
| 安全性（越狱、注入攻击） | MKE 管知识内容质量，不是安全网关 |

## 为什么"外挂"是正确的架构选择

### 不是所有问题都适合在 LLM 内部解决

```
选项 A：修改 LLM 架构，内置知识持久化和冲突检测
  → 需要重新训练 → 只能解决未来模型的问题 → 无法复用到已有模型

选项 B：外挂 MKE，与 LLM 独立演进
  → 不需要改 LLM → 任何模型都能用 → MKE 的改进独立于模型
```

这和 bim 森林的"互补学习系统"设计原理一致——海马体（快速编码）和新皮层（慢速巩固）是两个独立的系统，通过 Consolidation Pipeline 交互，而非互相替代。

### MKE 是"基础设施"而非"框架"

```
Dify/LangChain = Agent 行为框架——管 Agent 怎么做事
MKE = 知识质量基础设施——管 Agent 用的知识对不对

消费关系：
  LLM → 通过 MKE retrieve() 获取知识 → 作为上下文注入 → 推理
       ↑
  MKE 不控制 LLM 的推理行为
```

## 和 lmp 森林消费者评估的呼应

`[lmp] MKE作为外挂记忆体的核心价值` 中的结论在这里完全适用：

> MKE 让知识"不被遗忘"，而不是让推理"变得更好"。

这两个是不同的目标。MKE 解决第一个，第二个留给模型能力代际提升。

## 坦诚缺口

| 缺口 | 说明 |
|------|------|
| MKE 的检索延迟对 LLM 对话体验的影响 | 无实测数据——渐进式检索的理论延迟在毫秒级，但缺少实际场景验证 |
| 如果 MKE 存储的知识本身有错误 | SSOT 管交叉声明，但不管单个知识原子的真值——source_count 是共识度不是真值度 |
| 如果用户不想让某条知识被持久化 | 当前架构中所有交互都记录在 Interaction_Memory——隐私/选择性遗忘策略未设计 |
