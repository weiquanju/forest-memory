# 性能影响与架构张力

## 性能影响

### 存储

| 对象 | 数量级 | 单条大小 | 总存储 |
|------|:---:|:---:|:---:|
| Leaf（当前） | N | ~2KB | 2N KB |
| Leaf（不变） | N | ~2KB | 2N KB |
| Assertion（新增） | N × 10~50 | ~200B | 2N~10N KB |
| **总增量** | | | **+1~5 倍** |

最坏情况：100 万文档 → 5000 万断言 → ~10GB 纯断言数据（含索引 ~15GB）。对单文件 SQLite 而言，这在 MVP 阶段可接受，规模化后可能需要分库。

### 查询

| 操作 | 复杂度 | 评估 |
|------|:---:|------|
| 新增断言时的去重检查 | O(log M) via B-tree on UNIQUE INDEX | ✅ ~100ns |
| 跨断言冲突检测（全量） | O(M²) pairwise 比较 | ❌ 50M² 不可行 |
| 跨断言冲突检测（簇内） | O(k²)，k = 簇大小 << M | ✅ 借助 Fact Cluster 限定范围 |
| 按 subject 检索 | O(log M) via index | ✅ 极快 |
| 断言图多跳遍历 | O(M × d²)，d = 平均度数 | ⚠️ 取决于连通度 |

**关键优化**：冲突检测不能全量 O(M²)，必须借助 Fact Cluster 将检测范围限定为簇内——这是 Fact Cluster 存在的关键理由之一。

### 抽取

| 阶段 | 当前 | 断言级 | 增量 |
|------|------|--------|:---:|
| LLM 原子化（Layer 1） | 1 次 API 调用/文档 | 不变 | 0% |
| LLM 断言提取（Layer 0） | 不存在 | 1 次 API 调用/文档 | **+100%** |
| 文档级去重（Layer 2） | 向量相似度 O(N) | 不变 | 0% |
| 断言级去重（Layer 0） | 不存在 | B-tree O(log M) | 极低 |

**结论**：性能瓶颈不在存储或查询，在抽取环节额外的一次 LLM 调用。断言提取可以批量处理以摊薄 API 调用成本。

## 三个新引入的架构张力

### 张力 1：Leaf 与 Assertion 的一致性

```
Leaf.content: "A18 在 Geekbench 6 单核得分 3200，较 A17 提升 28%"
Assertion:    {A18, geekbench6_single_core, 3200}
              {A18, perf_gain_vs_a17, 30%}   ← 与 Leaf 不一致！

二者谁为准？维护同步有持续成本。
```

**方向**：Leaf.content 为权威来源（SSOT 第一层）。Assertion 为抽取物（SSOT 第二层）。不一致时以 Leaf 为准，标记断言待修正。

### 张力 2：治理粒度不一致

```
Leaf A 有 30 条 Assertion（数据密集型）
Leaf B 有 0 条 Assertion（纯论述型，不适合三元组）

在质量治理和检索时，A 和 B 的行为完全不同，
但它们在 MKE 中应该是同级的"知识细胞"。
```

**方向**：接受这种不一致——断言的覆盖度取决于原文的知识类型。不适合三元组的知识不强制断言化。

### 张力 3：置信度的哲学问题

```
source_count=47 的断言如果后来被证伪？
  → source_count 本身是"共识度"，不是"真值度"
  → 需要区分 consensus vs veracity

LLM 抽取器给出的 confidence：
  → 模型自评不可靠（RLVR 校准退化已证实）
  → 谁来校准 confidence？
```

**方向**：source_count 和 confidence 作为两个独立维度。source_count 来自结构化统计（可靠），confidence 来自 LLM 自评（不可靠，需标注）。长期需要外部验证信号（如引用 retraction、下游性能反馈）。
