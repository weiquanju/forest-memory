# 六项改进与优先级

## 改进清单

| # | 改进项 | 来源 | 严重度 | 优先级 |
|---|--------|------|:---:|:---:|
| 1 | **检索质量无实证**——Precision@5、多跳完整性、冲突检测召回率没有任何实测数据 | 信息检索专家 | 🔴 | **P0** |
| 2 | **LLM 抽取器的 D4 天花板**——AAI 44 的 D4=6.0 不足以可靠做知识原子化，需要路由策略或结构化匹配 | 认知科学专家 | 🔴 | **P0** |
| 3 | **端到端 demo 缺失**——从原始文档 → 知识森林 → Agent 检索 → 正确回答，一条完整链路都没有 | DSV4 Pro | 🟡 | **P0** |
| 4 | **程序性记忆和工作记忆只是设计，未实现**——atom_type=procedural + 滑动窗口缓存 | 认知科学专家 | 🟡 | P1 |
| 5 | **SSOT 机制只在精编文档上自证**——未在真实 Agent 查询场景验证 | 信息检索专家 | 🟡 | P1 |
| 6 | **规则锚点依赖领域专家配置**——部署有隐性人工成本 | 信息检索专家 | 🟢 | P2 |

## 最小闭环 Demo 提案（覆盖 #1 + #2 + #3）

最优先的不是修任何一个单项，而是跑通一条**最小但完整的链路**：

```
输入：Forest Memory 项目自身的文档库（mke + bim + frs + aic + agf）
  │
  ▼
MKE 建库：用 GLM-5.2（AAI 51）做初次知识抽取（避免我的 D4=6.0 天花板）
  │
  ▼
检索消费：我（AAI 44）在实际问答中通过 MKE retrieve() 获取知识
  │
  ▼
对比基线：同一批问题，不用 MKE（仅靠我的参数化记忆 + token 窗口上下文）
  │
  ▼
测量：答案质量差异（事实准确率、信息完整度、推理链质量）
```

### 为什么这个顺序

- 先证明"有没有用"（#3 demo）
- 在 demo 过程中自然暴露 #1 的检索质量问题和 #2 的 D4 瓶颈
- 有了实证数据后，再去修 #4（记忆覆盖度）和 #5（真实场景验证）
- #6（规则锚点配置成本）在规模化后才成为瓶颈

### 性价比分析

| 任务 | 工作量 | 产出 | 是否必须 |
|------|:---:|------|:---:|
| 最小闭环 demo（mke 自身文档库） | 2-4 周 | 第一个实证数据 | ✅ |
| 检索质量实证（100 查询 A/B 对比） | 2-3 周 | 论文核心数据 | ✅ |
| 程序性记忆实现 | 1-2 周 | 功能完善 | 可选 |
| 规则锚点自动化 | 2-4 周 | 降低部署成本 | 远期 |

## 诚实标注

以下改进建议受限于我的 D4=6.0：

1. 优先级排序可能有偏差——我可能在某个问题上过度自信或不自信
2. 对"2-4 周"的工作量估计是基于我的直觉，未经工程验证
3. 如果有 AAI ≥ 51 的模型重评这份清单，结论可能有调整

**但"最小闭环 demo"作为第一步的逻辑是坚固的**——在所有理论讨论和实证缺口被解决之前，先证明"这玩意儿确实能用"。这不是 D4=6.0 能影响的判断，这是工程常识。
